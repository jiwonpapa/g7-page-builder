# G7 Page Builder 차수별 구현·개선 계획

2026년 8월 31일 · 실행 계획 v2.1 · 1차 실행 착수

형님, 편집기는 TypeScript·React, 저장·검증·발행은 PHP입니다. 이번 개선은 **계약 우선 설계 + 시험 우선 구현 + 작은 기능의 처음부터 끝까지 검증 + 차수별 통합** 방식으로 진행하는 것이 맞습니다. TypeScript를 쓴다는 사실이나 테스트 도구가 있다는 사실만으로 체계적인 개발이 보장되지는 않습니다.

이 문서는 앞선 제품 방향 보고서의 P0~P3를 **8개 차수와 내부 배치**로 구체화한 실행안입니다. 원래 계획 v2의 제품 코드 미착수 상태에서 1차 계약 문서 task를 시작했습니다. 현재 판정은 [추진 상태](README.md)와 [1차 증거](phase-1-evidence.md), 구체적 결정은 [편집 정책](editing-policy.md)·[호환 결정](compatibility.md)·[콘텐츠 기준](content-policy.md)을 우선합니다. 2026-08-31 추진 지시에 따라 차수별 검증·자동 커밋·통합 상태를 보고하고 순차 진행합니다. 범위 확대·파괴적 이행·운영 배포·사람의 시각 승인은 별도 경계를 유지합니다.

**v2 변경:** 형님 요청에 따라 G7 레이아웃 편집기의 참고할 설계를 기존 배치의 요구사항·재사용 단위·합격 조건에 반영했습니다. G7 편집기나 코드를 가져오거나 Puck을 교체하는 계획이 아닙니다. 참고 설계는 우리 PageBuilderDocument·Puck·PHP 계약에 맞춰 구현하며, 이번 변경은 계획 문서에만 적용했습니다. 아래 현황 수치·활성 task는 v1 조사 시점의 기록이므로 구현 착수 시 다시 확인합니다.

## 1. 사용하는 언어와 책임

| 구성 | 실제 기술 | 책임 |
|---|---|---|
| 관리자 편집 화면 | TypeScript + React + Puck | 블록 선택, 직접 편집, 중첩 배치, 속성 패널 |
| 글자 단위 편집 | Puck 필드 안의 Tiptap | 선택한 글자의 폰트·크기·색·링크와 문서 변환 |
| 디자인 | 범위가 제한된 CSS + typed 디자인 값 | 여백·배치·반응형·편집/공개 표현 일치 |
| 저장 원본 | PageBuilderDocument JSON | 내용·구조·스타일·버전을 표현하는 공통 문서 |
| 서버 | PHP 8.5 | 입력 검증, 권한, 저장·동시 수정, 컴파일·발행·복원 |
| 개발·빌드 | Node 24 + Vite, Vitest, PHPUnit, Playwright | 타입 검사·시험·배포 파일 생성·실제 브라우저 확인 |

현재 설치본은 TypeScript 5.9.3, React 19.2.8, Puck 0.23.0입니다. 설정은 TypeScript strict이며 Puck은 정확한 버전으로 고정되어 있습니다. 고객 서버에서 TypeScript를 실행하는 구조가 아닙니다. 개발 환경에서 JavaScript·CSS로 빌드해 배포하고 서버 요청은 PHP가 처리합니다.

TypeScript는 실행 전에 잘못된 값 사용을 찾는 도구입니다. 빌드 후 타입 정보는 없어지므로 외부 JSON·API 입력의 안전성은 별도 실행 시 검증과 서버 검증이 담당해야 합니다. React는 UI를 재사용 가능한 컴포넌트로 나누는 수단이지, 컴포넌트만 쪼개면 설계가 좋아진다는 뜻은 아닙니다. [TypeScript 공식 설명](https://www.typescriptlang.org/docs/handbook/typescript-from-scratch.html), [React 컴포넌트](https://react.dev/learn/your-first-component).

## 2. 현재 기반과 보완할 점

확인 기준은 main 8b75d3a654638bfeb932985f67f8106ef05c8c42, 제품 0.30.0입니다. 이번에는 기존 전체 시험을 재실행하지 않았으므로 아래는 설정·코드 존재의 확인이지 현재 모든 시험의 성공 보고가 아닙니다.

### 이미 있는 기반

- G7와 분리된 Domain / Application / Contracts / Infrastructure 계층.
- PageBuilderDocument 원본과 Puck 변환 어댑터.
- 공통 BlockAppearance·pageDesignTokens·canvasEditingContract.
- 기존 미디어·경로 선택기, 문서함·복제·Page Kit, optimistic lock을 사용하는 저장 계약.
- TS strict, Vitest, PHPUnit, PHPStan, CSS 검사, 실제 포인터 E2E, 편집/공개 레이아웃 비교.
- task별 파일 소유권, Worktree 제출, 단일 runtime 통합, final SHA 릴리스 게이트.

### 다음 개선에서 보완할 부분

- PuckEditorAdapter.tsx는 3,433줄, HtmlDocumentCompiler.php는 3,333줄입니다. 길이 자체가 결함 증거는 아니지만 추가 기능의 책임을 계속 집중시킬 위험이 있습니다. 새 기능과 맞닿는 변환·트리 검증·레이아웃 컴파일부터 분리합니다.
- 편집기·PHP·schema·CSS의 값과 규칙이 달라지지 않도록 같은 계약 fixture로 검사해야 합니다.
- 현행 본문 중첩 거부를 화면에서만 해제하지 말고 저장·발행까지 함께 연결해야 합니다.
- 콘텐츠의 의미 심사와 출력물의 렌더 심사를 분리해야 합니다. 기존 aggregate approved를 새 정책의 항목별 승인으로 자동 승격하지 않습니다.
- 파일을 분리하면서 핵심 코드가 기존 파일별 coverage 기준을 벗어나는 일이 없도록 이동된 코드에도 검사 책임을 옮깁니다.

현재 확인한 활성 작업은 rich-boundary-20260831, wysiwyg-media-20260831, wysiwyg-optional-20260831 및 Local 통합 담당 wysiwyg-media-integration-20260831입니다. 공개 CSS, Puck 어댑터, 여러 블록 렌더러, 시험과 품질 문서가 이미 소유되어 있습니다. 이 계획을 이유로 다른 작업을 중단·수정·강제 해제하지 않습니다.

## 3. 개발 방법론: 작업 순서를 고정합니다

이 프로젝트에는 다음 방식을 적용합니다. Scrum 같은 명칭이나 회의 횟수보다 실제 제출 조건이 중요합니다.

1. **계약 우선:** 무엇을 입력하고 어떤 결과가 나와야 하는지 먼저 정합니다. 허용 자식, 기기별 상속, 저장 데이터, 오류 상태까지 포함합니다.
2. **사례 우선:** 정상·경계·실패 사례를 문서/fixture로 만듭니다. ‘열을 줄일 때 사라진 열의 내용은 어떻게 되는가’ 같은 정책을 코딩 전에 결정합니다.
3. **시험 우선:** 순수 로직·버그 수정은 재현 시험이 먼저 실패하는 것을 확인하고, 최소 구현 후 통과시킨 뒤 정리합니다. 정적 UI·카피는 눈으로 확인할 합격 기준과 렌더 fixture를 먼저 둡니다.
4. **작은 완결 기능:** 어댑터만, 화면만, PHP만 끝났다고 제품 완료로 표시하지 않습니다. 최소 사례라도 편집 → 저장 → reload → 공개 출력까지 연결합니다.
5. **기존 기능 보존 후 분리:** 기존 동작을 고정하는 시험을 먼저 추가하고 필요한 부분만 모듈로 추출합니다. 전체 재작성, 대규모 폴더 이동, 사용처 없는 추상화는 하지 않습니다.
6. **차수별 통합:** 작은 배치를 검증·제출하고, 차수 끝에 사용자 시나리오와 공개 결과를 확인합니다. 막힌 기능을 둔 채 블록 수 확대 단계로 넘어가지 않습니다.

### 한 배치의 고정 작업 카드

모든 구현 배치는 다음 항목을 먼저 작성합니다.

- 요구사항 ID와 사용자 동작.
- 이번에 바꾸는 것 / 바꾸지 않는 것.
- 기준 SHA, 소유 파일, 필요한 AREA, 검증 profile.
- 재사용할 기존 모듈과 새로 만들 최소 모듈.
- 문서·API·버전·기존 데이터 영향.
- 정상/경계/실패 fixture와 예상 결과.
- 자동 검사와 실제 화면 시연 항목.
- 승인 근거를 재사용할 항목과 새로 심사할 항목.
- 실패 시 기존 상태 보존·배포/데이터 복구 방법.
- 완료 증거와 다음 차수 진입 조건.

서로 독립적인 기능 둘은 한 배치에 묶지 않습니다. 계획 중 소유 범위를 넘는 수정이 필요하면 범위 충돌을 재확인하고 새 작업 단위로 계획합니다.

## 4. 재사용 설계: 어떤 것을 한 번만 구현할 것인가

| 재사용 단위 | 원칙·사용처 |
|---|---|
| 문서·구조 계약 | JSON Schema·typed metadata·공통 fixture로 TS/PHP의 허용 값과 실패 조건을 일치시킵니다. |
| 문서 트리 조작 | 탐색·이동·복제·삭제·새 ID 발급을 순수 함수로 분리해 레이어, 캔버스, 패턴 삽입이 함께 사용합니다. |
| 구조 정책 | 허용 자식·깊이·열 비율·기기별 옵션을 한 정책 원장으로 정하고 UI와 서버 검증이 따르게 합니다. |
| 공통 표현 | BlockAppearance와 디자인 토큰을 확장합니다. 블록마다 별도 폭·간격·상속 계산을 만들지 않습니다. |
| 편집 필드 | canvasEditingContract의 필드 경로·최소/최대·미디어·링크 기능을 재사용합니다. |
| 화면 컴포넌트 | 값 선택·상속/초기화·부모 선택·미디어 조작 UI를 역할별 React 컴포넌트로 재사용합니다. |
| 외부 연결 | 기존 MediaPort, 경로 선택기, G7 Adapter만 사용합니다. 블록마다 업로드·인증·URL 처리기를 새로 만들지 않습니다. |
| 콘텐츠 공급 | 패턴은 구조+props+자산 참조 데이터로 만들고, 같은 구성의 색상 차이는 variant로 처리합니다. |
| 시험 자료 | 같은 원본 fixture로 schema·왕복 변환·PHP 출력·브라우저 결과를 확인합니다. |

**중요한 경계:** React 렌더 코드를 PHP 서버에서 실행하거나 PHP와 TypeScript 코드를 억지로 한 코드로 합치지 않습니다. 공유하는 것은 문서 계약·허용 값·스타일 규칙·시험 사례입니다. 브라우저와 서버는 각각 자기 책임을 구현하고 결과의 일치를 시험합니다.

새 레이아웃 기능의 모듈 이름 후보는 documentTree, layoutPolicy, layoutFields, layoutBlocks, LayoutTreeValidator, LayoutBlockCompiler입니다. 이것들은 아직 생성하지 않은 설계 이름이며, 실제 파일은 1차 책임 설계와 착수 시 파일 소유권 검사 후 확정합니다. 기존 Registry와 Port를 우선 사용하고 새로운 플러그인 프레임워크는 만들지 않습니다.

### 금지할 편법

- DOM 값을 긁어 저장 원본을 만드는 방식, Puck 내부 비공개 상태에 의존하는 방식.
- 타입 오류를 숨기기 위한 any·ts-ignore·강제 캐스팅 남발. 외부 값은 unknown에서 검증 후 좁힙니다.
- 같은 버그를 블록마다 별도 조건문·CSS 덮어쓰기로 고치는 방식.
- 공통 이름만 붙인 거대 utils 파일, 필요성이 없는 클래스 계층.
- 시험 skip, 검증 대상 제외, coverage 분모 축소로 통과시키는 방식.
- 샘플 문구·이미지 URL·사업 수치를 UI 로직에 하드코딩하는 방식. 예시는 manifest/fixture에 둡니다.
- 언어·엔진 교체를 제품 요구사항 해결의 대체물로 삼는 방식.

| G7R-06 | 문서/선택/저장 상태 분리와 변경 단위 | 기존 저장·Undo/Redo를 유지하면서 선택·편집·저장의 책임과 한 조작의 이력 단위를 명확히 합니다. | 4-C, 8-A | 저장 중 연속 편집·충돌·재진입·Undo/Redo를 확인하고 사용자 수정이 유실되지 않습니다. |
| G7R-07 | 미지정 기본값과 명시적 빈 값 구분 | 필드별 미지정/빈 값/삭제/초기화 의미를 정하고 목록 첫 변경 시 기본 항목이 의도치 않게 사라지지 않게 합니다. | 1-C, 3-C, 5-B, 6-A | undefined와 허용된 빈 배열·빈 문자열을 구분합니다. 필수 필드의 빈 값은 오류이며 기본값으로 숨기지 않습니다. |
| G7R-08 | 실제 렌더러 기반 미리보기 | 우리 구조에서는 canonical fixture·CSS/토큰 계약을 공유하고 JSX와 PHP 출력의 의미·크기·줄바꿈을 비교합니다. | 2-B, 4-B, 6-C, 8-A | 편집 전용 효과를 제외한 내용·구조·적용 스타일이 편집/미리보기/발행본에서 일치합니다. |

**도입하지 않는 부분:** G7 내부 import·전역 런타임 교체, 별도 dnd-kit 레이아웃 엔진, 자체 contentEditable/Tiptap 대체물, 별도 히스토리 엔진, G7 액션/바인딩 DSL, 임의 CSS·HTML·JS, 임의 breakpoint, 기기별 별도 콘텐츠 트리입니다. 다크 모드 신규 편집 축·표/폼/탭 내부의 자유 구조 편집도 이번 참고 설계 도입으로 자동 추가하지 않습니다. Puck의 공개 기능과 기존 공통 필드를 우선 사용합니다.

코드 복사·G7 규격 전체 수용·새로운 범용 플러그인 프레임워크가 아니라 **정책을 데이터로 선언하고 기존 구현이 그 정책을 일관되게 따르도록 하는 개선**입니다. 각 요구사항은 아래 배치의 완료 조건이며, G7에서 작동한다는 이유로 우리 구현의 시험을 생략하지 않습니다.

## 6. 1차 — 제품 계약과 구현 기준선 확정

**목적:** 이후 코딩에서 새 정책을 즉흥적으로 만들지 않도록 합니다.

### 배치 1-A · 현행 작업과 기준 SHA 정리

- 현재 활성 task의 제출·통합·미완료 범위를 읽고 기존 담당 흐름에서 정리합니다.
- 통합된 기준으로 현재 글자 선택·이미지 교체·저장 동작을 다시 확인합니다. 아직 안 된 부분과 새 개선을 구분합니다.
- schema/컴파일/편집 왕복의 기존 fixture와 핵심 E2E 시간을 측정합니다. 이 단계에서는 검사 범위를 줄이지 않습니다.
- 신규 구현은 충돌 파일이 해소된 clean 기준 SHA에서 시작합니다. 문서 검토는 그 전에도 할 수 있습니다.

### 배치 1-B · 편집 정책 결정

- G7R-01~04: 블록별 편집 능력·부모/자식 허용표·공통 컨트롤·기기별 상속을 기존 계약의 어느 필드가 책임질지 대응표로 확정합니다. 별도 중복 metadata 원장을 만들지 않으며 부족한 선언만 버전된 계약으로 확장합니다.
- 블록·슬롯·필드·반복 항목의 ID와 선택 경로를 구분합니다. 새 기본 타입은 선언과 시험 없이는 노출하지 않고, 기존 선언 부족 항목은 호환을 보존한 채 6~7차 처리 원장에 배정합니다.
- 내용 편집 / 명시적 구조 편집의 차이, Section → Columns → Stack → 기본 요소 문법을 확정합니다.
- 초기 열은 1·2·3열과 대표 비율, Section 안의 레이아웃 단계는 Columns·Stack 두 단계로 제한합니다.
- 열 수 축소 시 내용은 자동 삭제하지 않습니다. 비어 있지 않은 열은 명시적 이동 확인 후 남은 열의 끝으로 합치고 문서 순서를 보존합니다. 취소하면 원본 그대로입니다.
- 반복 항목 이동 시 내용뿐 아니라 해당 요소 스타일의 연결도 보존하도록 정합니다.
- PC 편집/기기별 미리보기 정책을 유지하면서, PC의 ‘기기별 설정’ 패널에서 모바일 옵션을 변경하는 경로를 정합니다.
- 캔버스 폭 1280/768/360과 브라우저 시험창 1440/768/390을 구분해 비교 대상의 실제 폭을 계약에 기록합니다.
- 새 schema version 필요 여부, block_version·compiler_version·Pack 최소 버전, 구형 원본의 읽기·편집·이행·복원을 결정합니다. 버전 번호를 추측해 올리지 않고 호환 분석과 결정 기록을 선행합니다.
- 기존 500개 최상위 블록 제한과 달리 중첩은 전체 노드 수를 세어야 합니다. 구형 문서 호환, 반복 항목 수, 문서 크기를 포함한 제한·오류 동작을 결정합니다.

### 배치 1-C · 콘텐츠 기준과 목록

- G7R-01·07: 각 항목의 편집 선언·안전 기본값·완성 데모·검증 상태를 함께 기록합니다. 필드별 미지정/빈 값/초기화 의미를 구분하고 기본값의 중복 정의·불일치를 검사할 fixture를 정합니다.
- 기존 95개를 기본 요소/틀/완성 섹션/시작 페이지 연결용으로 분류하고, 배포/후보/재작업/호환 상태를 기록합니다. 아직 심사하지 않은 것을 승인하지 않습니다.
- 기존 service-conversion, local-business, editorial-community를 우선 기준 페이지로 정합니다. 기존 company-launch·event-launch는 7차로 남깁니다.
- 완성 화면의 구조·카피·이미지·모바일 기준안을 만들고 합격/불합격 사례를 정합니다. 시안은 제품 기능 구현·출시 승인이 아닙니다.
- 샘플 수치·후기 교체 정책과 원본/데모/default 값 구분을 확정합니다.

**산출물:** 기존 제품 명세·편집 계약·콘텐츠 계약의 변경안, 요구사항-시험 대응표, 호환 결정 기록, 카탈로그 처리 원장, 다음 배치의 정확한 파일 범위.

**검증/완료:** 정책 간 충돌, 누락된 저장/복원 경로, 미정 필드가 없고 대표 화면 기준이 합의되어야 합니다. 현재 시험의 실패는 고정된 알려진 실패 목록으로 남기고 숨기지 않습니다. 적용 문서는 docs profile, 계측/fixture 코드는 해당 코드 profile로 분리합니다.

**제외:** Puck 교체, 신규 카탈로그 양산, 중첩 구현, 운영 배포.

## 7. 2차 — 검증·승인 재사용 기반

**목적:** 콘텐츠를 고치기 전에 불필요한 심사 반복을 줄일 구조를 만듭니다.

### 배치 2-A · 검토 증거 분리

- 현재 단일 승인 객체를 콘텐츠 의미·권리 심사와 렌더/편집 검증 증거로 구분하는 버전된 계약을 만듭니다.
- 콘텐츠 심사는 문구·이미지·용도·샘플 주장·공급 유형 변경에 의존하도록 합니다. 공개 CSS만 바뀌었다고 문구 의미 심사를 다시 요구하지 않도록 합니다.
- 렌더 검증은 CSS·컴파일러·props·이미지 변화에 계속 의존합니다. 화면이 바뀌었는데 이전 화면 승인으로 통과시키지 않습니다.
- 기존 승인 이력은 출처가 있는 과거 기록으로 보존하며 새 기준의 전수 합격으로 자동 이행하지 않습니다.

### 배치 2-B · 변경 영향 원장과 계측

- G7R-05·08: 블록/계열별 상태 fixture ID와 적용 여부·제외 이유를 영향 원장에 연결합니다. 기본·긴 한국어·빈 목록·미디어 없음·최소/최대 항목·capability 부재 등 필요한 상태를 정하고 원격 랜덤 이미지나 현재 시각에 의존하지 않게 합니다.
- fixture는 시험용 공급 경계에서만 주입합니다. 로그인·API·문서 저장·발행을 임의로 바꾸는 전역 상태 교체를 사용하지 않으며, 동적 블록의 실제 데이터 연동 확인은 별도 통합 시험으로 유지합니다.
- item ID → 디자인 계열 → 렌더러/필드 계약 → CSS/토큰 → 시험/증거의 대응표를 만듭니다.
- 단계별 실행 시간, 영향 항목 수, 재실행 이유, 검토 시간을 기록합니다.
- 처음에는 기존 전체 검사와 나란히 영향 계산 결과를 비교합니다. 의존성이 불명확하면 전체 대상으로 처리합니다.
- 공통 CSS 전체 해시의 제거는 이 차수의 자동 목표가 아닙니다. 실제로 영향이 분리되어 입증된 범위만 선택 검증 대상으로 전환할 수 있습니다.

### 배치 2-C · 검증기 자체 회귀

- G7R-05: 필수 상태 fixture 누락·삭제·오래된 렌더 증거·실제 API로의 샘플 누출을 실패 사례에 포함합니다. 시험 fixture 추가/변경도 영향 판정 대상이며 샘플 화면 통과를 실제 G7 연동 성공으로 표시하지 않습니다.
- 문구 변경, 미디어 교체, 한 계열 CSS 변경, 공통 토큰 변경, compiler 변경, 삭제된 증거를 각각 시험합니다.
- 바뀐 항목의 오래된 승인 거부, 미변경 콘텐츠 심사 재사용, 알 수 없는 변경의 넓은 검증, 누락 dependency의 실패를 확인합니다.
- 현행 45/95/140 재고 상수는 무작정 삭제하지 않습니다. 3차에 허용할 구조 기본 타입과 새 공급 분류를 반영한 버전된 예상 목록으로 관리합니다.

**주요 범위:** schemas/block-product-quality.schema.json, product-quality.json, 관련 검사·썸네일 스크립트, tests/Harness, docs/quality-harness.md. 정확한 claim은 실제 분할 후 확정합니다.

**검증/완료:** 검증기 실패 사례가 모두 실패하고 기존 안전 게이트가 유지되어야 합니다. mixed 또는 full 범위로 검증하며 마지막 전체 릴리스 검사는 면제하지 않습니다.

**제외:** 자동으로 approved 채우기, 해시 삭제로 통과시키기, 브라우저 전수 시험의 근거 없는 생략.

## 8. 3차 — 최소 중첩 기능을 끝까지 연결

**목적:** 작은 실제 사례로 설계가 작동하는지 입증합니다.

### 배치 3-A · 변환·검증 책임 추출

- G7R-01·03: 편집 능력과 구조 규칙을 해석하는 순수 로직을 기존 Registry/필드 계약에 연결합니다. TypeScript 타입뿐 아니라 API 실행 시 검증과 PHP 검증도 공통 fixture를 따르게 합니다. UI가 지원하지 않는 필드를 숨기는 것만으로 입력 검증을 대신하지 않습니다.
- PuckEditorAdapter에서 필요한 순수 문서 변환을 분리하고, PHP 컴파일러에서 트리 검증·레이아웃 처리를 분리합니다.
- 먼저 기존 평면 문서의 왕복·컴파일 동작을 fixture로 고정합니다.
- 문서 트리 탐색·이동·복제·삭제·ID 처리와 구조 정책을 별도 순수 로직으로 구현합니다. Puck의 DnD·히스토리 자체는 재구현하지 않습니다.
- 새 파일로 이동한 핵심 로직에도 기존 이상의 시험 책임을 유지합니다.

### 배치 3-B · 최소 수직 기능

- Section 하나, 2열 Columns 하나, 제목/본문 등 최소 기본 요소만 연결합니다.
- Canonical Document ↔ Puck slot 변환, 서버 입력 검증, PHP 출력, 저장·reload·preview·publish·revision 복원을 연결합니다.
- 기본 카탈로그 전체에 바로 개방하지 않고 검증용 문서와 명시적 내부 진입 경로부터 시험합니다. 미지원 구조를 저장에서 조용히 버리지 않습니다.
- 기존 구형 문서를 열기만 해도 강제 재저장·전체 변환되는 동작은 금지합니다.

### 배치 3-C · 경계·복구 시험

- G7R-02·07: 빈 컨테이너 첫 자식 삽입, 선언 없는 부모/자식 거부, 기본 목록의 첫 편집 보존, 명시적 빈 값의 왕복을 시험합니다. 같은 구조 허용표에 대해 팔레트 삽입·드롭·문서 변환·서버 검증 결과를 대조합니다.
- 잘못된 자식 타입, 깊이 초과, ID 중복, 큰 문서, 불법 slot, 복제·이동·삭제를 검증합니다.
- 자기 하위로 부모 이동 금지, 복제 시 새 ID, 이동 시 기존 ID·스타일 보존을 확인합니다.
- 기존 평면 문서·SEO·shell mode·revision 정보를 잃지 않는지 확인합니다.
- 컴파일 실패 시 마지막 정상 발행본의 내용과 해시가 유지되어야 합니다.

**주요 범위:** resources/js/documents, PuckEditorAdapter와 새 문서 트리 모듈, schemas/page-builder-document.schema.json, src/Domain/Documents, Application/Compilation, tests/Contract·Unit·UnitPhp·Integration·E2E.

**검증/완료:** 공통 JSON fixture의 TS/PHP 판정 일치, 왕복 동일성, 최소 문서 실제 발행·복원 통과. shared-contract AREA와 필요 시 migration AREA를 사용하고 full profile로 닫습니다.

**형님 시연:** 2열 제목 수정 → 저장 → 새로고침 → 공개 페이지 → 이전 revision 복원.

**제외:** 45종 내부 중첩 개방, 모든 디자인 옵션, 사용자 패턴 저장.

## 9. 4차 — 구조·반응형 편집을 사용할 만하게 완성

**목적:** 시험용 중첩을 실제 운영자가 다룰 수 있는 기능으로 만듭니다.

### 배치 4-A · 구조 조작

- G7R-01·02: 팔레트·레이어·캔버스·속성 패널이 같은 편집 능력 선언을 읽게 합니다. 추가/이동 가능 여부와 실패 이유가 진입 경로마다 달라지지 않게 하며, 이동 후 선택은 이동한 요소를 따라갑니다.
- Stack과 1/2/3열·대표 비율을 추가하고 기본/구조 편집 모드, 부모 선택 경로·레이어를 연결합니다.
- 허용 drop 표시, 잘못된 삽입 이유, 열 축소 시 내용 이동 확인, 빈 컨테이너의 안내를 제공합니다.
- 제목·본문·이미지·버튼 등 허용 기본 요소만 조합합니다. 폼·탭·슬라이더·G7 데이터는 기존 복합 블록으로 둡니다.

### 배치 4-B · 반응형·공통 스타일

- G7R-03·04: 공통 컨트롤은 값·허용 범위·변경·오류 표시의 계약을 공유하며 최소 대표 블록 2종에서 재사용을 입증합니다. 위젯 확장은 기존 등록 경계에서 처리하고 블록명별 if/switch 또는 동적 실행 코드를 추가하지 않습니다.
- 기기별 지정값의 초기화는 현재 공통값 복사가 아니라 override 제거입니다. 공통값 출처와 현재 지정 여부를 표시하고 ‘모바일 초기화 → 공통값 변경 → 모바일 반영’, ‘다른 기기의 지정값 보존’을 시험합니다. 기기별 콘텐츠 복제나 새로운 다크 모드 편집 범위를 추가하지 않습니다.
- 기존 BlockAppearance·pageDesignTokens를 확장해 열·간격·패딩·정렬·줄간격·크기 단계의 규칙을 통일합니다.
- 전역 → 블록 → 요소 → 기기별 값의 우선순위와 상속/직접 지정/초기화를 구현합니다.
- PC의 설정 패널에서 모바일 값을 지정하되 모바일 캔버스 직접 편집은 계속 막습니다.
- 동일 콘텐츠를 기기별로 복제하지 않으며 시각 순서와 읽기·포커스 순서의 충돌을 제한합니다.
- 편집용 JSX와 PHP 출력에 같은 CSS 규칙을 적용하고 computed style·줄바꿈·실제 폭을 비교합니다.

### 배치 4-C · 직접 편집·미디어·저장 회귀

- G7R-06: 한 번의 이동·열 변경·패턴 삽입 등 논리적 조작은 한 Undo 단위가 되도록 기존 Puck 공개 API 경로에서 검증합니다. 텍스트 입력 묶음·조합 입력의 히스토리 경계는 기존 필드 동작과 합의하고 저장 성공만으로 이력을 무조건 비우는 G7 동작을 그대로 따르지 않습니다.
- 선택 상태·미저장 문서·저장 요청 버전을 분리해 실제 시나리오로 검사합니다. 저장 중 편집은 유지하고 충돌/실패 후 내용 보존·안내·재시도·문서 전환이 계약대로 동작해야 합니다. 기존 구현이 통과하면 새 상태 관리 라이브러리나 히스토리 엔진을 추가하지 않습니다.
- 통합된 기존 글자 범위 편집·이미지 기능을 재사용하고 새 중첩에서도 확인합니다. 완료된 기존 패치를 재작성하지 않습니다.
- 글자 일부 스타일과 요소 전체 스타일, 한글 입력 조합, 툴바 클릭, 부모 선택, Undo/Redo의 충돌을 검사합니다.
- 반복 항목 순서 변경 후 해당 문구·사진·요소 스타일의 연결이 유지되는지 확인합니다.
- 이미지 교체·비우기·대체 텍스트·비율·fit·제한된 초점 조정을 기존 미디어 경로에 연결합니다.
- 자동 저장 중 편집 차단, 늦게 온 저장 응답의 덮어쓰기, 저장 실패·동시 수정 충돌·이탈 안내를 시험합니다.

**검증/완료:** 실제 포인터 E2E, 키보드/포커스, 편집·preview·공개 일치, 긴/짧은 한국어와 항목 수 변화 통과. 핵심 구조/표현을 함께 건드리므로 full 통합 검증을 기본으로 하고 범위가 독립된 순수 UI 배치만 frontend로 분리합니다.

**형님 시연:** 3열→2열 변경해도 내용 보존, 모바일 1열 설정·초기화, 한 문장 일부만 서식 변경, 이미지 교체 후 재진입.

**제외:** 임의 CSS·HTML·JS, 자유 좌표, 임의 breakpoint, 이미지 편집 앱 내장.

## 10. 5차 — 사용자 패턴 재사용과 라이브러리 구분

**목적:** 잘 만든 구역을 매번 다시 만들지 않게 합니다.

### 배치 5-A · 패턴 원본·저장 계약

- Section subtree를 HTML이 아닌 canonical 데이터로 저장합니다.
- 제목·분류·미리보기·원본 버전·필수 block/asset 참조를 포함합니다.

- 기존 Page Kit import/export의 검증·자산 해석 기능을 재사용합니다. Section 패턴을 외부 Code Pack으로 취급하지 않습니다.

### 배치 5-B · 저장·삽입·독립 수정

- G7R-02·07: 패턴을 현재 삽입 대상의 부모/자식 허용표로 검증하고 미지정값·명시적 빈 값의 의미를 보존합니다. 복합 패턴 일부만 삽입되거나 기존 기본 목록이 한 항목으로 대체되는 실패를 차단합니다.
- ‘구역 저장 → 내 패턴에서 선택 → 다른 페이지에 삽입’을 연결합니다.
- 삽입 시 subtree 전체 ID를 새로 발급하고 원본 패턴이나 다른 페이지와 독립적인 복사본을 만듭니다.
- 패턴 삭제가 이미 삽입된 페이지의 내용·미디어를 없애지 않도록 자산 참조와 보존 정책을 검증합니다.
- 버전·블록 capability가 맞지 않으면 이유를 표시하고 부분적으로 깨진 삽입을 하지 않습니다.

### 배치 5-C · 카탈로그 정보 구조

- G7R-01·03: 편집 가능 항목·제한 안내를 실제 편집 능력 선언에서 구성합니다. 카탈로그 설명과 편집 패널이 따로 하드코딩되어 어긋나지 않게 하며, 복합 블록에 구조 편집이 가능한 것처럼 표시하지 않습니다.
- 기본 요소 / 레이아웃 틀 / 완성 섹션 / 시작 페이지 / 내 패턴을 의미 있게 구분합니다.
- 용도별 검색·필터, 정확한 렌더 미리보기, 편집 제한·샘플·필수 capability 표시를 연결합니다.
- 기능이 없는 블록의 제어 항목은 비활성 이유를 보여 주거나 숨깁니다. 같은 스타일 variant를 별도 완성형 항목으로 과장하지 않습니다.

**검증/완료:** 저장·삽입·문서 reload, 다른 페이지 독립 수정, ID·미디어 참조, 미지원 버전과 권한 실패. 저장 계약 변경을 포함하므로 full 및 필요 shared-contract/migration AREA를 사용합니다.

**형님 시연:** 만든 2열 소개 구역을 저장해 다른 페이지에 넣고, 한쪽만 수정해도 다른 쪽은 유지됩니다.

**제외:** 전역 동기 패턴, 타 사이트 간 동기화, 공유 마켓·유료 거래 기능.

## 11. 6차 — 대표 콘텐츠부터 제품 수준으로 완성

**목적:** 대량 재작업 전에 공통 설계와 품질 기준이 실제로 통하는지 확인합니다.

### 배치 6-A · 기존 대표 프리셋 6개

현재 존재하는 다음 항목부터 개선합니다.

1. hero.service-intro — 첫 화면의 대상·가치·다음 행동.
2. rich-text.article-intro — 실제로 읽을 수 있는 소개 본문.
3. image-text.company-story — 문구와 사진이 연결된 회사 이야기.
4. features.core-benefits — 차별점과 특징의 정보 구조.
5. card-grid.services — 서비스 선택과 비교에 적합한 카드.
6. cta.contact — 앞선 내용과 연결된 문의 행동.

- 새 타입 양산이 아니라 기존 항목의 문구·이미지·위계·기본값·편집 계약을 개선합니다.
- G7R-07: 목록 등의 기본값은 기존 manifest/계약의 지정 출처를 재사용합니다. 렌더러의 실제 기본값과 선언의 불일치를 시험으로 막고, 항목 첫 추가·삭제·의도적 비우기를 저장/reload 후에도 확인합니다.
- 안전한 기본값과 완성 데모를 분리하고 이미지 권리·샘플 수치 교체 사항을 기록합니다.
- 공통 기능 결함이 나오면 임시 블록 전용 우회로 처리하지 않고 해당 기능 차수의 결함 배치로 되돌립니다.

### 배치 6-B · 기존 시작 페이지 3개

- service-conversion: 서비스 설명 → 장점 → 근거 → 상담.
- local-business: 장소·제공 서비스 → 방문 정보 → 문의/길찾기.
- editorial-community: 사이트 성격 → 콘텐츠 탐색 → 게시판/본문 진입.

각 페이지가 실제 사업/운영 문맥으로 이어지도록 기존 구성과 자산을 개선합니다. 페이지가 사용하는 추가 섹션도 동일 기준으로 검토하며 필요 목록은 1차에 확정합니다. ‘대표 프리셋 6개만 고치면 3개 페이지의 모든 내용이 합격’이라고 처리하지 않습니다.

### 배치 6-C · 기준 심사

카피·목적·시각 위계·이미지·콘텐츠 변화·반응형·편집 완결성·접근성·표시 정확성의 9개 조건으로 판정합니다. 배포 가능/수정 필요/배포 불가와 항목별 근거를 남깁니다.

- G7R-01·05·08: 각 대표 항목에서 선언한 편집이 실제로 가능한지 확인하고 2차 상태 fixture로 편집/미리보기/발행본을 비교합니다. 미적 합격과 동작 합격을 분리해 기록하며, 완성 데모 한 장의 합격을 모든 상태의 승인으로 확장하지 않습니다.

**검증/완료:** 자동 검사와 실제 화면 검토를 둘 다 통과해야 합니다. 3개 기준 페이지의 품질을 먼저 확인하고 이후 같은 기준의 반복 작업은 위임 가능한 체크리스트로 만듭니다. 테스트 통과를 형님의 시각 승인으로 대신하지 않습니다.

**주요 범위:** builtin-core manifest·품질 기록·해당 자산, resources/store/source/page-kits와 관련 fixture·썸네일. 콘텐츠/프런트 변경의 실제 profile과 기존 게이트를 적용하고 차수 말에 사용자 흐름을 통합 검증합니다.

**제외:** 95개 일괄 승인, 경쟁사 코드·사진 무단 복제, 새로운 업종 확장.

## 12. 7차 — 나머지 카탈로그를 작은 배치로 정비

**목적:** 기존 콘텐츠를 빠짐없이 처리하되 무조건 전부 다시 만들지는 않습니다.

### 배치 묶음

- 7-A: Hero·CTA 등 첫 화면/전환 계열의 남은 변형.
- 7-B: 기본 본문·이미지/텍스트·기능/카드 등 콘텐츠 계열.
- 7-C: 회사·신뢰·수치·요금·비교 계열. 샘플 실적/후기 검토 포함.
- 7-D: 미디어·내비게이션·문의·위치 계열.
- 7-E: G7 데이터 계열. 실제 capability 존재/부재와 빈 결과·오류 상태 포함.
- 7-F: 남은 company-launch·event-launch 시작 페이지와 전체 라이브러리 연결 확인.

각 묶음은 같은 렌더러·레이아웃 규칙을 공유하는 항목끼리 더 나눕니다. **실제 실행 배치의 상한은 8개 프리셋**으로 제안하며 복잡한 상호작용이 있으면 더 작게 나눕니다. 이는 업계 표준이나 속도 예측이 아니라 검토 가능한 작업량을 닫기 위한 운영 한도입니다. 정확한 ID 목록은 1차 원장과 6차 결과로 확정합니다.

G7R-01·05: 각 배치는 편집 능력 선언과 계열별 상태 fixture를 공통으로 사용합니다. 7-E의 G7 데이터 계열은 capability 존재/부재·빈 결과·오류의 미리보기와 실제 Adapter 연동을 구분해 검증합니다. 선언·필수 사례·렌더 근거가 누락된 항목은 신규 노출 합격으로 처리하지 않고 기존 문서 호환은 보존합니다.

### 배치별 처리

- 유지: 새 기준으로 확인 후 근거를 부여합니다.
- 수정: 내용/디자인/편집 결함을 해당 계열의 공통 규칙으로 해결합니다.
- 통합: 실질 차이가 없는 항목은 variant로 정리하되 기존 ID 해석은 보존합니다.
- 후보/호환 유지: 신규 삽입 노출을 제한하되 과거 문서·revision·발행본은 깨지지 않게 합니다.

각 항목은 정확히 하나의 배치와 상태를 가져야 합니다. 기존 95개, 새 구조 기본 요소, 향후 추가 패턴의 재고를 구분합니다. 합격 수를 늘리려고 호환 전용 항목을 신규 제품 수에 넣지 않습니다.

**검증/완료:** 목록 누락·중복 배정 0, 신규 노출 항목의 미해결 필수 결함 0, 기존 ID·자산·문서 호환 유지. 계열 공통 변경은 해당 계열 전체를 검사하고 불명확한 영향은 넓게 검사합니다.

**제외:** 배치 중 몰래 새 기능 추가, 일정 맞추기용 승인 일괄 갱신, 원본 ID·사용 중 자산 삭제.

## 13. 8차 — 전체 회귀와 릴리스 후보 종료

**목적:** 개선된 편집기·콘텐츠·검증 정책이 함께 작동하는 제품을 닫습니다.

### 배치 8-A · 제품 전수·성능

- G7R-05·06·08: 상태 fixture의 격리, 기존 저장/히스토리 연계, 편집/공개 일치를 최종 제품 흐름에서 재검증합니다. UI에서 불허한 조합을 API로 제출하는 부정 사례도 포함해 선언과 실제 서버 정책의 일치를 확인합니다.

- Header/Footer, template/builder/none shell, 선택 G7 capability 부재, 로그인 전후 표시, 발행 실패 시 정상본 보존을 확인합니다.
- 작은/대표/큰 문서에서 입력 반응·조작·저장·미리보기 전환을 같은 환경으로 측정합니다. 지원 노드 한도와 확인된 한계를 공개합니다.
- 보호된 관리자 자격증명은 증거에 포함하지 않습니다. 공개용 결정적 fixture로 시각 증거를 남깁니다.

### 배치 8-B · 검증 효율 검증

- 2차의 변경 영향 계산과 실제 전체 결과를 비교합니다.
- 선택 검사에서 놓친 오류가 있으면 dependency를 보완하고 범위를 넓힙니다.
- 내용 심사 재사용·스타일 계열 검증의 실제 절감 시간과 누락 결함을 보고합니다. 측정 전 절감률을 약속하지 않습니다.
- 과거 승인 증거가 새 버전의 잘못된 성공 근거로 재사용되지 않는지 확인합니다.

### 배치 8-C · 릴리스 후보·배포 경계

- 모든 제출 task가 통합된 final SHA에서 integration-verify를 실행합니다.
- 버전/CHANGELOG/asset manifest와 배포 패키지, schema/compiler 호환, 업그레이드·복구 절차를 확인합니다.
- 배포는 승인된 대상·범위 안에서만 수행합니다. 배포 승인 전에는 ‘릴리스 후보 검증 완료’라고 보고하고 운영 배포 완료와 구분합니다.
- 새 문서를 구버전 바이너리가 읽을 수 없다면 바이너리만 되돌리는 것을 안전한 rollback으로 주장하지 않습니다. 마지막 정상 발행본 유지, 편집 중지, 수정 버전 전진 또는 검증된 백업 복원 경로를 분리합니다.

**완료:** 약속한 사용자 작업·기존 문서 호환·콘텐츠 합격선·실패 복구가 모두 입증되고, 승인된 배포를 수행했다면 배포 후 공개 흐름까지 확인되어야 합니다.

## 14. 시험 정책과 구현 품질 판정

### 필요한 시험 네 층

1. **단위시험:** 트리 이동/복제, ID, 상속 값 계산, 스타일 경로, 샘플 상태 판정 같은 순수 로직.
2. **계약시험:** 동일 JSON의 TS/PHP 허용·거부, schema 버전, Canonical ↔ Puck 왕복, PHP 출력 의미.
3. **통합/컴포넌트 시험:** 선택 상태·저장 상태·필드 변경·미디어와 경로 Adapter, 저장소 동시 수정.
4. **브라우저/시각 시험:** 실제 마우스·키보드·한글 입력, preview/공개 동일성, 모바일/중간 너비, 오류 회복.

### 새 기능의 최소 실패 사례

- G7R-01~08의 구현 배치·시험 ID·증거·미해결 상태를 요구사항-시험 대응표로 추적합니다. 참고 자료를 읽었다는 사실이나 선언 파일 생성만으로 요구사항 완료를 표시하지 않습니다.
- 블록이 선언한 컨트롤이 다른 블록의 필드를 수정하지 않으며, 미선언 편집·금지 부모/자식 조합을 API로 우회할 수 없습니다.
- 미지정값과 유효한 빈 값이 구분되고, 기본 목록의 첫 변경이 나머지 기본 항목을 없애지 않습니다.
- 기기별 초기화 후 공통값 변경을 상속하며, 다른 기기의 명시적 값은 유지됩니다.
- 샘플 상태 변경이 실제 관리자 인증·문서·발행 상태로 누출되지 않습니다.
- 허용하지 않은 자식·깊이·중복 ID가 거부됩니다.
- 형제 요소의 내용·스타일이 뜻하지 않게 바뀌지 않습니다.
- 열을 줄이거나 블록을 옮겨도 내용이 없어지지 않습니다.
- 이전 저장 응답이 새 편집 내용에 덮어쓰지 않습니다.
- 문서를 다시 열면 구조·스타일·SEO·shell·revision이 유지됩니다.
- 선택형 capability·미디어·네트워크 실패가 다른 문서나 기존 공개본을 깨뜨리지 않습니다.
- 스타일 변경으로 콘텐츠 의미 승인까지 불필요하게 무효화되지 않지만 필요한 렌더 검증은 빠지지 않습니다.

현재 coverage 최저선은 frontend 전체 lines 56%, 핵심 Puck 어댑터 lines 81%, PHP 전체 lines 61%이며 PHP 주요 영역은 별도 하한이 있습니다. 이는 설정된 바닥선이지 제품 완성도 점수나 현재 달성 결과가 아닙니다. 숫자를 올리기 위한 무의미한 assertion보다 새 계약의 정상·경계·실패 분기를 빠짐없이 검사해야 합니다.

## 15. 통합·변경·승인 운영

실행 시 기존 하네스를 따릅니다.

1. clean 기준 SHA에서 정확한 PATHS와 PROFILE, 필요한 shared-contract/migration/version AREA를 claim합니다.
2. Worktree에서 배치 구현과 검증을 수행하고 task-submit으로만 제출합니다.
3. Local integration/runtime 소유자가 task-integrate로 순차 통합합니다.
4. 상호 의존하지만 파일 소유가 겹치지 않는 제출물이 꼭 함께 검증되어야 할 때만 기존 task-integrate-batch를 사용합니다.
5. 모든 작업 통합 후 integration-verify로 final SHA를 검증합니다.
6. 후속 코드 변경이 있으면 해당 증거를 다시 만들며 release guard를 우회하지 않습니다.

새 기능이 필요해지면 요구사항 ID·필요 사례·기존 기능으로 해결할 수 없는 이유·문서/시험/유지 비용 영향을 기록한 뒤 다음 차수로 편성합니다. 당장 편하다는 이유로 현재 배치의 범위를 몰래 넓히지 않습니다.

형님이 확인할 결과는 소스 줄 수가 아니라 다음 항목입니다.

- 약속한 동작이 실제 화면에서 되는가.
- 저장하고 다시 열어도 그대로인가.
- 공개 페이지도 같은가.
- 다른 블록과 기존 문서가 깨지지 않았는가.
- 실패했을 때 사용자 내용과 정상 발행본이 남는가.
- 공통 기능을 수정할 때 한 곳의 규칙으로 해결되는가.

## 17. 일정과 당장 착수할 범위

지금 전체 완료 날짜를 확약할 근거는 없습니다. 활성 작업의 실제 완료 상태, 최소 중첩 경로의 난도, 콘텐츠 한 계열의 심사 시간이 아직 함께 계측되지 않았습니다.

- 1차: 선행 작업·기존 실패·검사 시간을 확인하고 차수별 범위를 닫습니다.
- 3차 종료: 기능 구현의 남은 작업량과 리스크를 다시 산정합니다.
- 6차 종료: 나머지 콘텐츠 작업량을 실제 재작업/유지/통합 수로 산정합니다.

**현재 실행 단위는 1차입니다.** 산출물은 확정된 편집 계약, 버전/호환 결정, 콘텐츠 처리 원장, 대표 기준 화면, 첫 코드 배치의 수정 범위·시험 목록입니다. 후속 차수는 이번 순차 추진 지시와 차수별 gate를 따르되, 운영 배포나 미정의 범위 확대까지 자동 허가된 것으로 처리하지 않습니다.
