# 1차: G7 일반 페이지·라우트·JSON UI 실증

검증일: 2026-09-05. 범위: 로컬 `g7pb.test`에서 격리된 일반 페이지와 기능 조합 페이지를 등록하고, G7 Layout Editor 편집·저장·재진입·미리보기·공개 출력을 확인한다. 제품 기능 구현 또는 외부 배포 차수가 아니다.

## 결론

**G7에 일반 페이지 생성 기능은 있으며, 새 JSON UI 페이지와 URL도 모듈 선언으로 등록할 수 있다. 등록한 페이지는 기본 Layout Editor에서 개별 편집된다. 부족한 부분은 사용자가 페이지 생성·주소 할당·메뉴 연결을 한 흐름에서 처리하는 제품 UI다.**

실제로 회사소개와 고객지원 페이지 두 개를 등록하고 본문을 직접 편집했다. 저장 HTTP 200, 편집기 재진입, 미리보기, 비로그인 공개 출력이 모두 확인됐다. 고객지원은 기존 G7 최신 글 API의 5개 항목과 일치하며 실제 게시글로 이동한다.

다만 **Page Builder가 런타임에 주입한 Site Shell 노드가 네이티브 편집기의 저장 원본에 섞이는 결함**을 두 페이지에서 재현했다. 기본 페이지 동작은 성공했으나, 현 상태를 테마 편집 연동의 안전성 통과로 판정하지 않는다. 수정은 후속 작업이며 이번 1차에서 제품 소스를 바꾸지 않았다.

## 기본 페이지 기능과 새 JSON UI 페이지의 차이

| 방식 | 원본과 주소 | 편집기 관계 | 이번 확인 |
| --- | --- | --- | --- |
| G7 기본 페이지 관리 | `sirsoft-page` 콘텐츠, `/page/:slug` | 각 페이지가 별도 레이아웃이 되는 구조가 아니라 `page/show`를 공유 | 생성 화면·현재 요청 규칙·템플릿 route와 데이터 바인딩 확인. 기존 페이지 8개 보존 |
| 모듈 소유 JSON UI 페이지 | 모듈의 user route + user layout, 모듈 lifecycle로 레이아웃 등록 | 모듈 그룹 아래 개별 항목으로 나타나 편집·저장 가능 | 두 페이지 등록 및 실제 브라우저 전체 흐름 확인 |
| Page Builder 제품 | `PageBuilderDocument` + 마지막 정상 발행본 | 독립 편집기, G7 네이티브 저장 원본과 분리 | 이번 실험에서 제품 문서/발행본 변경 없음 |

기본 페이지 생성 화면에는 URL slug, 다국어 제목·본문, 첨부·SEO 등의 입력이 있다. 요청의 slug는 영문 소문자·숫자·하이픈만 허용한다. `/company/about` 같은 자유 경로 등록 기능과는 다르다.

현재 G7 admin layout API는 기존 레이아웃 GET/PUT, preview, revision/restore를 제공한다. 이번에 확인한 API 목록에는 새 route/layout을 만드는 endpoint가 없으며, `LayoutService::updateLayout()`도 등록되지 않은 레이아웃이면 실패한다. 따라서 "G7에는 일반 페이지 자체가 없다"는 판단은 부정확하고, "네이티브 편집기에서 페이지를 생성하고 새 주소를 배정하는 흐름이 없다"가 이번 확인 범위에 맞다.

## 등록 방법과 JSON UI 계약

실험은 G7 공식 lifecycle을 사용했다. 기존 템플릿 JSON이나 DB 레이아웃을 직접 수정하지 않았다.

1. 고유 모듈의 `module.json`, `module.php`, `composer.json`과 두 user layout을 준비했다.
2. `resources/routes/user.json`에 `path`와 `layout`을 선언했다.
3. `_bundled/jiwonpapa-site_phase1`에서 `module:install`로 설치했다.
4. 초기 실험 문서의 텍스트 위치를 실제 native 계약에 맞춰 `0.1.1`로 수정하고, 해당 실험 모듈만 `module:update --source=bundled`로 갱신했다. 다른 모듈·전체 템플릿 refresh는 실행하지 않았다.
5. `module:activate` 결과 새 레이아웃 2개가 등록됐다. 역할·권한·관리자 메뉴는 추가하지 않았다.

등록에 사용한 핵심 선언은 다음과 같다.

```json
{
  "version": "1.0.0",
  "routes": [{
    "path": "*/phase1-20260905/about",
    "layout": "phase1_about",
    "auth_required": false,
    "meta": {"title": "1차 회사소개 검증"}
  }]
}
```

라우트 선언의 키는 `layout`, 문서 내부 식별자는 `layout_name`이다. 활성화 뒤 라우트에는 `jiwonpapa-site_phase1.phase1_about`처럼 모듈 접두사가 붙는다. 서버의 기존 catch-all이 등록 여부를 확인하므로 별도 Laravel web route를 추가할 필요가 없었다.

고객지원은 `_user_base`의 `slots.content`에 정적 설명과 아래 계약을 조합했다.

- `data_sources`: 공개 `GET /api/modules/sirsoft-board/boards/posts/recent?limit=5`.
- `iteration.source`: `{{recent_posts.data ?? []}}`, `item_var`: `post`.
- 문구: 노드의 `text`, 예: `{{post.title}}`. 임의 `props.text`로 간주하지 않는다.
- 클릭: 기존 `navigate` handler와 `/board/{{post.board_slug}}/{{post.id}}`.
- 데이터·인증·게시글 저장 기능을 복제하지 않았다. 기존 API를 읽고 실제 G7 화면으로 이동한다.

이번 결과는 이 제한된 JSON UI 범위를 소스와 화면으로 검증했다는 의미다. 모든 컴포넌트·중첩 구조·폼·권한·쇼핑몰·전체 테마를 자유롭게 왕복 편집할 수 있다는 보증은 아니다.

| 검증 | 회사소개 | 고객지원 |

| 신규 URL HTTP 응답 | 200 | 200 |

두 페이지 모두 본문에 `수정 완료 · 1차 검증` 문구가 남아 있다. Native 편집 중에는 샘플 데이터가 보이며, 고객지원 캔버스는 샘플 글 3개를 보여준다. 별도 preview와 공개 페이지에서 실제 API의 5개 항목을 확인했다. 캔버스의 샘플만으로 기능 연동 성공을 판단하지 않았다.

공개 검증은 관리자 세션과 분리된 비로그인 브라우저 context에서 수행했다. 실제 API 항목 ID는 `17, 16, 15, 13, 14`이며 5개 제목 모두 화면에 존재했다. 게시글은 생성·수정하지 않았으나 실제 열람에 따른 조회수/로그 등의 정상 부수효과는 가능하다.

반응형 초기 렌더 직후에는 아직 모바일 배치가 보일 수 있어, 최종 이미지는 데이터 로드와 네트워크 안정화 뒤 다시 캡처했다. 1440 폭은 desktop header, 768·390 폭은 mobile header로 확인했다. 실제 이미지도 열어 문구 줄바꿈·목록·헤더/푸터를 확인했다. 자동 시각 회귀 전체 suite나 디자인 완성도 승인을 수행한 것은 아니다.

공개 6회 최종 검사에서 `pageerror`는 0건이었다. 브라우저 전체 세션 로그에는 로그인 전에 발생한 admin auth/layout 401 두 건이 남아 있다. 따라서 세션 전체 오류가 0건이라고 보고하지 않는다.

Native 레이아웃의 Save는 별도의 제품 초안 발행 단계를 거치지 않고 공개 결과에 반영됐다. 구매용 킷·테마에 필요한 초안/미리보기/명시적 발행 정책은 별도로 설계해야 한다.

## 발견한 결함: 런타임 노드의 저장 혼입

**판정: 재현됨, 미수정. 테마 편집 연동 전 필수 차단 항목.**

재현 순서:

1. `_user_base`를 상속하는 실험 모듈 layout을 G7 Layout Editor에서 연다.
2. 본문 P 노드의 문구만 직접 수정한다.
3. Save를 누른다.
4. PUT 응답과 모듈 소유 DB row의 `content`를 확인한다.

원래 실험 파일에는 없던 `g7pb_global_site_header`, `g7pb_global_site_footer`가 두 문서의 `slots.content`에 저장됐다. 이 노드는 `g7pb_site_shell`을 참조하지만, 저장된 문서의 `data_sources`에는 해당 source가 없다. 회사소개는 source 자체가 없고 고객지원은 `recent_posts`만 남아 있다.

소스와 연결되는 원인:

- `G7SiteShellLayoutBridge`가 공식 `core.layout_extension.after_apply`에 등록한다. 현 구현은 editor 조회와 공개 조회를 구분하지 않는다.
- G7 `LayoutService::getLayout()`은 `withSourceMeta` 편집 조회에서도 extensions/post-apply를 적용한다.
- `UserTemplateSiteShellDecorator`는 Site Shell 노드를 생성하지만 네이티브 편집기의 source 분리 메타를 부여하지 않는다.
- G7 `layoutTreeUtils.ts`는 저장 시 route 소유 또는 출처 메타가 없는 신규 노드를 보존한다. 주입된 노드가 신규 페이지 노드처럼 취급되는 것이 관찰 결과와 일치한다.

현재 페이지 문구와 게시글은 정상 출력된다. 그러나 주입 ID가 이미 존재하면 decorator가 조기 반환하므로, 이후 Site Shell 연결/교체에 영향을 줄 가능성이 있다. 실제 유료 테마나 활성 빌더 셸을 전환해 영향 범위까지 시험하지는 않았다. **현재 확인한 저장 오염과 향후 셸 장애 위험을 구분한다.**

후속 수정의 완료 기준은 "기존 G7 편집 내용을 저장해도 런타임 노드/source가 원본에 들어가지 않음, 공개 화면에서는 정상 주입, 재진입/재저장 및 마지막 정상 발행본 보존"이다. 원본 소유권을 보장하는 공개 연동 경로를 먼저 확인하고, 임의 내부 runtime import나 사후 문자열 제거를 제품 계약으로 삼지 않는다.

## 기존 상태 보존

검증 전후 파일과 행 전체의 SHA-256을 비교했다. 원본 값이나 비밀정보를 증거에 출력하지 않았다.

- 기존 템플릿, G7 services/repositories, frontend source, route 파일 **3,478개**: 변경 0개.
- 기존 G7 layout **144개**: 변경 0개. 실험 모듈 row 145·146은 소유 식별자로 별도 분리했다.
- 기존 기본 페이지 **8개**: 변경 0개.
- PB 문서 **142개**, 리비전 **458개**, 발행본 **90개**: 변경 0개.
- PB Site Part/셸 및 기타 `g7pb_*` 테이블: 기존 행 변경·추가 없음.
- G7 Layout Extension **41개**: 변경 0개.
- 실험으로 모듈 등록, 모듈 레이아웃 2개, 해당 revision 4개, preview 2개 및 custom translation이 추가됐다. 이 부수 데이터는 보존한 로컬 검증 결과다.

전체 DB 무변경을 주장하지 않는다. 인증·미리보기·번역·활동 로그·모듈 lifecycle 데이터는 정상적으로 변경될 수 있다. 전체 템플릿 refresh, 기존 DB 직접 UPDATE, 코어 소스 수정, 제품 버전 변경, 외부 배포는 수행하지 않았다.

## 2차 우선순위와 완료 기준

ROI 판단은 이번 실증의 의존관계와 구현 범위에 따른 정성 판단이며, 매출이나 개발 시간 수치를 추정하지 않았다.

1. **먼저 저장 경계 결함 차단:** 네이티브 편집과 빌더 셸이 함께 있어도 원본이 오염되지 않음을 좁은 회귀 검증으로 확보한다.
2. **페이지 생성 → 주소 할당 → 편집 → 미리보기 → 발행:** 고유 페이지 1개를 사용자가 파일·Artisan·JSON을 만지지 않고 만들도록 연결한다. 기존 PB 문서/발행 기능을 먼저 재사용한다.
3. **메뉴 연결과 충돌 처리:** 공개 API로 가능한 범위를 확정한 뒤 사용자가 생성한 페이지를 찾아 메뉴에 연결하고 실제 이동한다. 관리자·API·기존 G7 경로 충돌은 저장 전에 설명한다.

2차 완료는 "사용자가 새 회사소개 페이지를 만들고 `/about` 같은 허용 URL을 지정해 메뉴에서 이동하며, 재진입·발행 실패 때 기존 정상 페이지가 보존됨"으로 판정한다. 모듈 fixture 파일을 자동 생성하는 것만으로 이 사용자 흐름을 완료 처리하지 않는다.

유료 킷 수량 확대, 풀 테마 상품 제작, 범용 JSON UI 편집기 재개발, 엔진 교체는 이 1차의 구현 범위에 포함하지 않았다.
