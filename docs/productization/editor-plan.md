## 범위와 유지할 기능

- 이번 계획은 편집 기능입니다. 새로운 판매 킷·풀 테마 상품·새 서버·결제/라이선스/배포 체계를 개발 순서에 넣지 않습니다. 후속 배포는 기존 라인을 사용합니다.
- 기존 Puck 커널, 인라인/Tiptap, 문서 명령·Undo, 미디어/링크 picker, G7 Adapter, canonical 저장/리비전/마지막 발행본을 확장합니다. 새 편집 엔진과 무제한 CSS/HTML/JS 편집은 제외합니다.
- PC 편집을 기준으로 합니다. 태블릿/모바일은 미리보기와 PC의 기기별 설정 대상입니다. 휴대폰 편집 UI와 기기별 독립 콘텐츠 트리는 이번 목표에 포함하지 않습니다.
- 현재 `layout/appearance` 반응형과 일반 요소 스타일을 보존합니다. 기기별 요소 스타일의 신규 확장은 암묵적으로 포함하지 않습니다.
- 기존 패턴·공통 Header/Footer·일반 페이지 주소·G7 목록·문의 기능은 재작성하지 않습니다. 새 구성과 만나는 조작/저장/공개 경로만 필요한 만큼 확장합니다.

## 출발점과 진척의 의미

기준 소스는 `58ed8a33829fdcb1327d730c6ab6da953f656949`입니다. 45개 정의·95개 preset·3개 구조 노드는 재고이고, 기능 완성률이 아닙니다. 기존 직접 편집·반복 항목·leaf5 중첩·패턴·SitePart가 있는 상태에서 새 목표를 추진합니다.

진척 원장의 **baseline은 기존 기반**, **items는 새 실행 항목**입니다. 문서 정리 완료를 편집 기능 완료로 세지 않으며, 항목 완료 수를 전체 제품의 퍼센트·작업 시간·사용자 만족도라고 해석하지 않습니다. 과거 기록에 남은 PASS/FAIL은 당시 증거이며 이번 요구에 필요한 관련 검증과 구분합니다.

## 개발 순서와 종료 조건

새 번호는 **EP1~EP4**만 사용합니다. 진행 보고는 **현재 차수/전체 4차 · 해당 차수의 세부 작업 순번/개수**로 표시하고, 다음 세부 작업과 다음 차수를 함께 적습니다. 세부 작업 11개를 11차수로 부르지 않습니다. 항목별 현재 상태는 이 표에 복제하지 않고 진척 원장에서 확인합니다. 각 항목은 작은 기능이라도 UI→명령→원본→저장→출력을 연결하는 단위입니다.

기본 선행 관계는 EP1-01→EP1-02→EP1-03→EP2-01입니다. EP2-02는 기본 요소 다음, EP2-03은 대표 카드의 슬롯 계약 검증 다음입니다. EP3 두 항목은 EP2 완료 후, EP4 첫 두 항목은 EP3 완료 후 진행하며 EP4-03은 나머지 항목 완료 뒤 수행합니다. 정확한 관계는 JSON이 정본이며 검사기가 누락·순환·완료 순서를 확인합니다.

같은 단계에서 의존관계가 없는 항목도 PATHS/AREA가 겹치면 병렬 구현하지 않습니다. 계획의 scope는 후보 파일이지 lease가 아닙니다. 착수 시 실제 코드·활성 task·base diff로 24개 이하의 정확한 파일을 claim하고, 공유 계약/버전/마이그레이션은 해당 AREA를 확보합니다.

## 첫 착수 카드: EP1-01

**문제:** 기술적인 definition/preset을 사용자의 제작 단위와 혼용합니다. 제목·버튼 preset까지 완성 섹션으로 보이고, 드로어와 상세 라이브러리가 다른 분류를 사용합니다.

**결과:** 기존 항목을 4개 제작 단위로 찾고, 노출된 편집 능력을 이해한 다음 삽입합니다. 외부 팩은 기존 manifest 버전을 그대로 읽을 수 있어야 하며, 분류 정보가 없는 항목의 호환 기본값/표시는 계약으로 정합니다. 기존 ID·preset 내용과 저장 문서는 재분류 때문에 바뀌지 않습니다.

**후보 파일:** `resources/js/blocks/types.ts`, `resources/js/blocks/builtinCatalog.ts`, `resources/js/editor/blockGalleryModel.ts`, `resources/js/editor/BlockGalleryControls.tsx`, `resources/js/editor/puckEditorConfig.tsx`, 해당 단위/브라우저 검사, `editor-progress.json`·상태판·CHANGELOG. manifest/schema가 꼭 필요하면 공개 계약 영향과 AREA를 먼저 정하고 claim합니다. 본문 슬롯·새 기본 요소·신규 킷은 이 항목에서 구현하지 않습니다.

**완료:** CAT-01의 관련 단위 검사와 실제 탐색/삽입 화면 증거, 각 타입의 5개 편집 능력 선언과 현재 지원/목표 표시 일치, 호환 팩/숨김 HeroSplit 보존, 같은 후보가 양쪽 삽입 UI에 나타나는지 확인합니다. 카드 목록은 현재 완성 조합이며 단일 카드 추가는 EP2-02입니다.

## 코딩 전에 각 작업에서 확정할 기술 결정

사용자에게 기능 범위를 다시 묻는 단계가 아니라, 정해진 정책을 기존 계약에 구현하는 작업의 일부입니다.

| 결정 | 담당 항목 | 반드시 남길 결과 |
|---|---|---|
| 제작 단위 metadata의 소유·구형 외부 팩 호환 | EP1-01 | 기존 descriptor/manifest 재사용 방식, 기본값, 중복 원장 없음 |
| 목록의 RichText 재사용 또는 독립 타입 | EP2-01 | 본문/목록 역할을 원본에서 검증할 수 있는 표현, 필요한 ID만 신설, 필드/한도/컴파일 매핑 |
| 슬롯 버전과 부모/자식 문법 | EP2-02 | 카드 슬롯·허용표·전체 subtree 깊이/개수 검사·TS/PHP 공통 fixture |
| 구형 props와 새 slots의 이행 | EP2-03 | 같은 콘텐츠를 두 곳에 저장하지 않는 매핑, 명시적 전환·취소·복원, 지원 버전/마지막 발행본 |
| 동작이 있는 자식의 편집/실행 구분 | EP3-01/02 | 탭/FAQ와 폼·G7의 허용 위치, focus·runtime 수명·오류 시나리오 |

EP2-03의 정확한 대상은 `content.hero-centered-01`과 `media.image-text-01`입니다. Hero의 현재 layout9개(poster/product/backdrop/editorial/device/balanced/screenshot/overlap/offset)와 ImageText의 기존 허용 변형 모두에서 새 슬롯의 내용 보존·저장/출력 호환을 확인합니다. HeroSplit는 구형 읽기/복원, HeroSlider는 기존 필드/반복 동작 보존 대상이며 신규 슬롯 대상이 아닙니다.

새 schema/block/compiler/최소 Pack 버전은 호환 영향을 확인한 뒤 기록합니다. 문서 계획 때문에 제품 버전 숫자를 미리 올리지 않습니다. 어떤 경우에도 raw HTML/JS·Puck 원시 상태를 새 원본으로 채택하지 않습니다.

검사는 실제 변경과 관련된 단위/PHP/브라우저/출력 시험을 선택합니다. 제품 소스 없는 문서 작업에서 제품 브라우저를 실행한 것으로 표시하지 않습니다. 테스트 파일 존재나 spec 수집, 정책 검사 통과, 컴파일만으로 사용자 조작 성공을 판정하지 않습니다. 전체 RC는 별도 사유와 기존 `FULL=1`/release guard를 따르며, 작은 수정 때문에 전체 회귀를 반복하지 않습니다.

## 진척 갱신 규칙

1. **착수 전:** `make editor-status`와 `make coord-status`를 읽고 항목 ID·scope·선행 완료·현재 코드 기준을 확인합니다. 담당 task와 `in_progress`를 기록할 문서 파일도 소유 범위에 포함합니다.
2. **구현 중:** 필수 사용자 흐름을 막는 원인만 `blocked`와 구체적 사유로 기록합니다. 단순 선행 대기는 `planned`를 유지합니다. 숨은 TODO나 체크박스만으로 진척을 대신하지 않습니다.
3. **검증·통합 후:** 실제 구현 commit과 통합 commit, 수용 기준별 시험 종류·대상 commit·결과·추적되는 증거 파일을 연결한 뒤 `done`으로 변경합니다. 아직 생기지 않은 문서 자신의 commit SHA를 요구하지 않습니다.
4. **증거 보존:** `output/`의 로컬 로그만 유일한 근거로 쓰지 않습니다. 실행 명령/환경/범위/결과/실패·미실행/원본 로그 위치를 담은 저장소의 검증 요약을 남깁니다. 민감 값은 담지 않습니다.
5. **상태판 갱신:** 원장을 수정한 뒤 아래 명령의 stdout을 명시적으로 저장하고 검사합니다. 표를 수동으로 따로 고쳐 숫자를 맞추지 않습니다.
6. **완료 변경:** 기준/범위 변경으로 완료를 되돌려야 하면 이유·영향을 기록하고 의존 항목 상태도 다시 판단합니다. 분모 삭제나 의존관계 제거로 완료 수를 부풀리지 않습니다.

```bash
python3 -B -m tools.g7pb.editor_progress status --markdown > docs/productization/editor-progress.md
make editor-plan-check
```

상태판 갱신은 해당 문서 소유 task에서만 합니다. 위 리다이렉션은 명시적 쓰기이며 `editor-status` 기본 조회의 부작용이 아닙니다. 기능 통합 이후 상태/증거만 갱신하는 별도 문서 task가 필요하면 기존 하네스로 제출·통합하며, 같은 입력의 성공 제품 검증을 다시 실행하지 않습니다.

완료 수는 기록된 증거의 정합성을 의미합니다. 검사기가 시험 결과의 진실성이나 자연어 정책의 모든 의미 충돌을 자동으로 입증하지는 않습니다. 실제 검증을 수행한 담당자가 근거를 남기고 검토해야 합니다. 배포 여부는 기존 release 기록으로 별도 보고하며 이 원장의 `done`으로 배포를 추정하지 않습니다.

## 문서 회귀 방지

- 정책 정본은 editing-policy.md, 실행 순서는 이 문서, 상태는 JSON 한 곳입니다. 상태판은 생성 결과입니다.
- 변경할 기능의 P-ID·EP-ID·수용 기준을 먼저 연결합니다. 블록/스타일/슬롯 정책 변경은 같은 작업에서 정본과 필요한 증거를 갱신합니다.
- 과거 roadmap/benchmark/차수 문서는 역사 안내와 현행 정본 링크를 유지합니다. 과거 실패·SHA·출시 여부를 현재 상태에 맞춰 고쳐 쓰지 않습니다.
- JSON·상태판·등록 문서·검사기 변경 시 기존 scoped planner가 문서 정합성 검사를 선택합니다. 동일 검사 입력의 성공만 재사용하고 문서/증거 내용이 바뀌면 다시 검사합니다.
- 기계 검사는 연결·상태·증거·정의된 marker의 정합성을 확인합니다. 본문 의미 변경은 정책과 실제 소스의 리뷰를 함께 수행합니다.

계획 수립 작업의 종료는 정본 반영·관련 하네스 검사·전체 문서 연결 확인·정식 통합으로 판정합니다. 개발은 EP1-01부터 순서대로 진행하며, 현재 착수 가능한 항목은 진척 원장에서 확인합니다.
