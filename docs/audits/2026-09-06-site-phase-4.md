# 4차: 일반 페이지와 G7 게시판 조합

대상은 로컬 `https://g7pb.test`, G7 7.0.9 / Page Builder 0.33.1의 Unreleased 개발 변경이다. 제품 구현은 `4afe42f7bfc5605527f76cbe8162eb6118d03b34`로 main에 통합했다. 외부 배포나 편집기 제품 완성 판정이 아니다.

## 구현과 사용 흐름

페이지의 `G7 최근 게시글` 블록에서 `전체 최신글 / 전체 인기글 / 지정 게시판`을 선택할 수 있다. 지정 게시판에서는 실제 G7 게시판 이름을 선택하고 문서에는 slug만 저장한다. 안내 문구·제목과 게시판 소식을 한 페이지에 배치하고, 기존 페이지 주소 설정으로 추가 주소를 할당한 뒤 발행한다. 게시글을 누르면 G7의 원래 게시글 화면으로 이동한다.

- 게시판 목록은 기존 공개 capability API, 게시글은 고정된 `/api/modules/sirsoft-board/boards/{slug}/posts` API를 사용한다. 임의 endpoint·인증 처리·HTML·JavaScript를 편집 필드로 추가하지 않았다.
- G7 게시판 API의 중첩 `data.data`와 최상위 게시판 정보를 해석한다. 공지 고정으로 API가 요청 수보다 많이 반환할 때도 블록의 최대 개수와 페이지당 개수를 지킨다. 제목은 DOM 텍스트로 출력한다.
- 기존 G7 인증 전송을 재사용하며 게시판 공개 여부와 권한은 G7이 판단한다. 목록을 불러오지 못하면 선택 상자를 비활성화하고 저장된 slug는 보존한다. 목록 새로고침으로 복구할 수 있다.
- 게시판 미선택 초안은 저장할 수 있고 미리보기·발행은 선택을 요구한다. 빈 게시판·권한 없음·게시판 없음·서버 오류는 해당 블록에서 안내하고 주변 일반 콘텐츠는 유지한다.
- PageBuilderDocument가 원본이다. `boardSlug`는 선택 필드이며 기존 전체 최신글·인기글 문서에 새 기본값을 강제로 쓰지 않는다. 기존 블록·프리셋 140개의 컴파일 결과는 이번 기능 전후 의미 해시와 source hash가 같았다.
- G7 기본 페이지 관리·기존 route·템플릿 파일·게시판 원본을 수정하지 않는다. 기본 `/pages/:slug`와 추가 주소 정책을 그대로 사용하고 활성 G7 테마가 기본 공통영역을 제공한다.

## 검증

최종 전체 통합 검사에서 Python 하네스 395개, PHP 356개(3,387 assertions), 프런트엔드 100파일·769개, coverage 하한선·타입·정적 경계·production build·asset 검사·G7 통합 검사가 통과했다. PHP의 기존 PHPUnit notice 1개는 실패가 아니며 제거했다고 주장하지 않는다. 기존 제품 브라우저 48개와 메뉴·인증·모바일 navigation 45개가 재시도 없이 통과했다.

선택 게시판 컴파일 전용 검사는 9개·25 assertions이다. 공개 데이터 조합 검사는 12개로 실제 응답 형태, 최대 개수, 인증, 빈 결과, 오류, 잘못된 응답과 제목의 안전한 텍스트 출력을 확인한다. 선택 상자 검사는 권한/기능 오류 복구·읽기 전용·저장값 보존과 반복된 vendor field ID에서도 라벨이 자기 입력을 가리키는 조건을 포함한다.

전체 제품 실행의 Site Part 보호 세션 16개는 모두 복원됐고 journal은 오류 없이 닫혔다. 기존 모듈 8개 테이블의 4,762행은 전체 검사 후 누락·변경 0개였다. 세트 활성 선택은 비교하고 `updated_at`·`updated_by`만 비교에서 제외했다. 근거는 `output/playwright/site-phase4-20260906/source-preservation-after-full9.json`이다.

새 조합 시나리오는 실제 G7의 `JWSoft RC 검증 게시판`과 기존 게시글 `JWSoft QA 20260902 기본 편집 전수`를 읽어 사용했다. 페이지 생성 UI → 새 페이지에 안내 섹션 준비 → 게시판 선택 UI → 저장·재열기 → 실제 데이터 미리보기 → 추가 주소 할당 → 발행 → 1440/768/390px 출력 → G7 원래 게시글 이동이 통과했다. 안내 섹션의 최초 배치는 이 시험이 소유한 새 문서에 API로 준비했고 게시판 선택·주소·발행은 화면에서 실행했다.

정상 흐름은 실제 API를 사용했다. 이후 같은 게시판 endpoint에만 빈 결과·403·404·500 응답을 제어해 오류 안내와 일반 콘텐츠 보존을 확인하고, 응답 제어 해제 뒤 실제 글 목록 복구와 저장된 선택값 보존을 확인했다. 실패 응답 시험을 실제 G7 권한 설정 변경 시험으로 해석하지 않는다. 브라우저 실행 오류와 가로 넘침은 없었다. 편집기·공개 페이지 3개 폭·게시글 화면·403 안내 이미지를 직접 확인했다.

신규 시나리오는 desktop 프로젝트 1개에서 31.6초, 재시도·skip 없이 통과했다. 관련 선택 상자 단위 검사는 7개다. 숨겨진 Puck 라디오 입력을 함께 찾는 선택자와 라디오 입력 위의 시각 label 문제는 실제 표시 label 클릭 후 선택 상태 확인으로 해결했다. 실제 편집기에서 선택 상자의 접근성 이름이 없던 제품 문제는 React 고유 ID로 라벨·상태 안내를 연결하고 공통 입력 스타일을 적용해 수정했다. 최종 수정 통합은 `dd5e8ba8ec340bdf851d954bdad29fa1715e2e04`이다.

- 검토용 페이지: <https://g7pb.test/support/phase4-1788699904096-desktop>
- 편집 문서: `0fb56153-2b81-43ee-88d0-c558038f92b6`
- 새 시나리오 증거: `output/playwright/gates/site-phase4-integration-20260906/8f694460da5cf9c82e1b3e47457ecb450f1a4ffb715f2c3c63e24208a7de75ae/40d3f3a696fc4b6a8aeb1a2a22a9b1f3/`. `execution.json`, 실제 Playwright report, `owned-support-page.json`과 화면을 보존한다.

`make integration-verify TASK=site-phase4-integration-20260906 FULL=1`이 `dd5e8ba8ec340bdf851d954bdad29fa1715e2e04`에서 통과했다. 로그는 `output/playwright/phase4-final-verification-2.log`다. 최초 최종 검사에서는 하네스의 시간초과 프로세스 종료 시험이 macOS `PermissionError`로 1회 중단됐다. 해당 시험 2개를 단독 실행해 통과했고, 제품 소스 변경 없이 최종 검증을 다시 완료했다. 이 실행 중단을 숨기거나 제품 브라우저 성공으로 대체하지 않았다.

모든 브라우저 검사 이후에도 기존 4,762행의 누락·변경은 0개이며, 근거는 `output/playwright/site-phase4-20260906/source-preservation-final.json`이다. 검토용 추가 주소는 마지막 HTTP 확인에서도 200이었다. 최종 실행의 Site Part journal은 16개 세션을 모두 복원하고 닫혔다. 이번 작업은 Unreleased 개발 통합으로 종료하며 원격 push·외부 배포는 실행하지 않았다.

## 별도 기준 정비와 남은 범위

기존 CSS 분리 뒤 오래된 테스트·카탈로그 생성물·시각 기준·전체 실행의 Site Part 보호 경로가 통합 검증을 막고 있었다. 별도 task로 수정했고 세부 근거는 [카탈로그 기준 정비](2026-09-06-catalog-baseline.md)에 기록했다. 썸네일 102개와 index·manifest를 재생성했으며 비교 허용치와 사람의 기존 승인 기록은 변경하지 않았다. 공개 CSS gzip 상한의 기존 초과분은 18,000 → 18,100 bytes로 명시적으로 조정했다. 성능 개선으로 보고하지 않는다.

이번 범위는 일반 콘텐츠 안에 선택 게시판의 글 목록을 조합하는 것이다. 게시판 글쓰기·댓글·검색 화면 자체의 편집, G7 기본 기능 화면의 자유 배치, 문의 처리 기능, 판매 결제·유료 킷 전달, 외부 사이트 킷 가져오기·내보내기, 전체 테마 호환성은 이 차수의 구현 범위에서 제외했다. 이후 문의 접수 수정은 [5차 기록](2026-09-07-site-phase-5.md), 현재 개발 범위는 [편집 고도화 실행계획](../productization/editor-plan.md)으로 구분한다. PC 편집과 공개 페이지의 반응형 출력 검증을 모바일 편집 지원이나 전체 제품 출시 승인으로 해석하지 않는다.
