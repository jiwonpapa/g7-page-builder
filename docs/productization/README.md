# Page Builder 제품화 추진

기준일: 2026-08-31. 시작 SHA: `8b75d3a654638bfeb932985f67f8106ef05c8c42`.

사용자는 G7 참고 설계를 포함한 8차 개선 계획을 1차부터 추진하고 차수별로 자동 커밋하도록 지시했습니다. 계획의 실행 단위는 유지하고, 차수별 결과를 섞지 않습니다. 소스 제출·통합·제품 합격·운영 배포는 서로 다른 상태입니다.

## 이번 1차 산출물

- [편집 정책](editing-policy.md): 편집 능력, 제한 중첩 문법, 공통 컨트롤, 반응형·저장 동작.
- [호환 결정](compatibility.md): v1 보존, v2 도입 조건, 버전·이행·복원·재사용 구역 저장 경계.
- [콘텐츠 기준](content-policy.md): 공급 분류, 9개 합격 조건, 대표 6개와 기준 페이지 3개.
- [재고·배치 원장](inventory.json): 현행 45개 블록·95개 프리셋·5개 Page Kit의 출처와 처리 배정. 제품 승인 원장이 아닙니다.
- [요구사항-시험 대응표](requirements.md): 각 요구사항의 구현 차수·사례·증거 기준.
- [기준선·실행 증거](phase-1-evidence.md): 이번에 확인한 상태, 실행한 검사, 미실행과 선행 조건.
- [전체 차수별 계획](roadmap.md): G7R-01~08을 각 배치에 연결한 실행안.

1차는 제품 코드를 변경하지 않습니다. 이 문서의 새 정책은 후속 차수의 구현 기준이며, v2 스키마·중첩·사용자 패턴 기능이 이미 실행된다는 뜻이 아닙니다. 현행 동작은 기존 명세와 시작 SHA를 기준으로 구분합니다.

## 차수 진행과 커밋

1. 차수별 정확한 파일 범위와 검증 profile을 소유한 worktree에서 작업합니다.
2. 필수 검사 뒤 `make task-submit TASK=<id>`로 자동 커밋·제출합니다. 수동 stage/commit으로 우회하지 않습니다.
3. integration/runtime 소유자가 통합 게이트를 통과시킨 뒤 다음 구현 기준 SHA를 정합니다.
4. 합의된 기술 범위 안에서는 이번 추진 지시에 따라 순차 진행·자동 커밋합니다. 범위 확대·파괴적 이행·운영 배포·사람의 시각 승인은 별도 권한/증거 경계를 유지합니다.
5. 기존 활성 작업의 dirty 파일·lease를 가져오거나 해제하지 않습니다. 차수의 필수 선행 조건이 충족되지 않으면 제출된 산출물과 남은 조건을 보고하며 다음 차수 완료로 건너뛰지 않습니다.

## 1차 종료 조건

| 조건 | 증거 |
|---|---|
| 정책·호환·제외 범위가 구체적이고 서로 일치 | 위 계약과 요구사항 ID |
| 현행 모든 항목이 정확히 한 처리 배치에 배정 | inventory ID 대조·누락/중복 0 |
| 기존 검증 기반과 실제 실패/미실행이 구분 | phase-1-evidence |
| 기존 편집 수정 통합 후 사용자 동작 재확인 | 통합 SHA와 실제 포인터·저장·공개 결과 |
| 대표 완성 화면의 기준이 검토됨 | content-policy의 기준 + 사용자 시각 확인; 자동 승인 금지 |
| 차수 자동 커밋·통합 상태가 추적됨 | task 제출/통합 SHA와 coord-status |

문서 제출만 끝난 상태를 1차 제품 합격으로 표현하지 않습니다. 한편 사람 확인을 기다리기 위해 이미 작성·검증한 1차 문서 커밋을 보류하지 않습니다.
